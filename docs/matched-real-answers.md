# Matched real-answer comparison

`15_matched_real_answers.py` compares fixed actions `(N, B)` on real, scored answers while the server carries matched background traffic at the two rates frozen by the [sustained calibration](sustained-calibration.md). It is step 3 of the mid-point baseline and the go/no-go test of the project: does the best fixed action change between light and heavy load by more than noise?

The logic is in `matched_real_answers.py`. It reuses the trace generator, cell order, runner and idle check of `matched_serving.py`, the answer generation and voting of `real_answer_validation.py`, the grader of `answer_scoring.py` and the sampler of `profiling_pass.py`. It never launches a server. **No router is evaluated.**

## Design

- **Questions.** `prepare` draws a fixed cohort with an equal number of questions per MATH level (default 50, ten per level) from id-sorted pools with a seeded generator. The cohort is written to `plan.json` before any run and is never chosen from outcomes. With `--proportional` the count per level follows the level mix of the full question set, so cohort accuracy estimates the full-set accuracy.
- **Target stream: real answers.** Each question is one target job per cell. An action with `N` samples sends `N` parallel requests with different seeds; the job's answer is the plurality of the valid boxed answers and the job finishes when the slowest sample does. `B=0` is one non-thinking completion capped at 2048 tokens. `B>0` thinks up to `B` tokens, then asks for the final answer in a second request, as in the original labelling. Generation is EOS-aware.
- **Background stream: the calibrated synthetic stream.** Poisson arrivals at the frozen rate, single requests at the reference budget with replayed lengths and `ignore_eos`, using prompts of questions outside the cohort. This is exactly the traffic the rates were calibrated on, and it is byte for byte the same in every cell of a block, which real background answers could not guarantee.
- **Blocks and cells.** A block is one seed at one rate. It holds a background-only control and every action, in a seeded random order. The order of the two rates is also shuffled per seed. Target jobs are evenly spaced over the window in a seeded question order, and that schedule is the same at both rates. The window length is the number of questions divided by the target rate (`--target-fraction`, default 0.05, of the contended rate).
- **Sample seeds** depend on the block seed, the question and the sample index only, so sample 0 of `(4,0)` uses the same seed as the single sample of `(1,0)`. Batching can still change sampled tokens.
- **Other background rates.** `run --rates LABEL=RPS ...` replaces the frozen pair with the named rates, for example two rates between them, to locate where an action stops being affordable. The target schedule still follows the calibrated contended rate, so it is identical to the schedule of a run at the frozen pair. Rates given this way are chosen by hand and must be reported as such.
- All traces and cell orders are written before the first cell runs. The server must be idle before and after every cell. `--deadline-epoch` stops the run before a cell that could not finish (see [Resuming](#resuming-an-interrupted-run)); only complete blocks are scored.

## Time-varying load

`run --schedules step square` runs one block per schedule instead of one per constant rate. The background rate then changes within each cell and follows the machine's frozen light and contended rates:

- **`step`:** light, then contended, then light, each a third of the measurement window.
- **`square`:** light and contended alternate in phases of `--phase-s` seconds (default 300), starting light. The last phase may be shorter.
- The warm-up runs at the light rate and is its own phase, `warmup`.

For the 150-question cohort on the 4080, the window is 1,218 s. That gives `step` three phases of 406 s each, and `square` gives light 300, contended 300, light 300, contended 300 and light 18 s.

- **Arrivals.** Background arrivals are Poisson at a piecewise-constant rate, generated by time rescaling. A unit-rate stream is drawn on the cumulative-rate axis and mapped back to time through the inverse of the cumulative rate. Prompts and lengths come from the same seeded streams as a constant-rate trace, so only the arrival times depend on the schedule. With a single phase, the trace equals the constant-rate trace up to rounding of the times.
- **Matching.** One trace per block, written before the first cell, is replayed by every cell of the block. The background is therefore identical across entries, and the target schedule is the same as at any constant rate.
- **Phase labels.** Every event carries its `phase`, for example `2-contended`, and its load level `phase_rate` (`light` or `contended`), both decided by its arrival time. A job that arrives near the end of a phase may finish in the next one.
- **Metrics.** The whole-window metrics are reported per schedule exactly as for a constant rate. `summary.json` also holds `phases`: the same entries and paired differences per schedule and load level, with bootstrap intervals. Each cell lists the background requests and p95 latency per load level. GPU seconds are attributed over the whole cell, so per-GPU-second values by phase are approximate.
- `--schedules` cannot be combined with `--rates`. `resume` refuses to continue a run whose schedules have changed. `assemble` accepts schedule blocks only when every source has the same phases and the same frozen rates.

## Per-job policies

`run --policies FILE` adds one cell per policy to every block; with an empty `--actions` the block holds the control and the policies only, which is how a baseline mixture is run on the seeds of an earlier controller run. A policy sets the action of each target job on arrival, from server load or from fixed shares. See [load-adaptive controller](load-adaptive-controller.md).

## Metrics (`score`)

Scoring is offline and requires `math_verify`, the grader used for the labels.

- **Correct within target:** the job completed, its voted answer is verified correct, and its latency from scheduled arrival to the last sample is within the latency target. Every scheduled job is in the denominator: timeouts, errors, censored jobs and jobs with no boxed answer count as misses, and are also reported by status.
- **Per GPU-second (headline):** correct-within-target jobs divided by the GPU seconds attributed to the target jobs. A job is attributed the cell's wall time (one GPU) times its share of all tokens generated in the cell. Prompt processing is not attributed separately.
- **Goodput per GPU-second (per cell):** target jobs correct within target plus background requests completed within target, divided by the cell's wall seconds. This is the view that includes what the action does to everyone else.
- Both are reported at the tight and the loose target (2x and 4x idle p95 from the calibration).
- **Intervals:** percentile bootstrap over questions. All seeds of a question are resampled together. Differences between two actions resample the same questions for both.

### Power-state check

A laptop GPU changes its power limit with the power mode, heat and reboots, and a cell at a lower power state is slower for reasons outside the experiment. The run therefore logs the machine state next to every GPU sample, and `score` checks it.

- **Logged per sample:** utilisation, memory, power draw, temperature, the enforced power limit, SM and memory clocks, and the active clock-event (throttle) reasons. These are read in-process through NVML (`pynvml`, which vLLM installs). The run falls back to `nvidia-smi` only when NVML does not load. On a loaded WSL machine, `nvidia-smi` stalled for seconds at a time, and in earlier 4080 runs whole cells lost their power samples that way. A field that the GPU or driver does not report is logged as null, never guessed. The cell summary reports the fraction of samples throttled by the power cap, by thermal limits and by hardware slowdown.
- **Rule:** a cell is **flagged** when its mean GPU power differs from the background-only control of its block segment by more than `--power-tolerance` (default 10%, relative), and **unknown** when either value is missing. The control carries the same background as every other cell in its block and keeps the GPU busy, so on one machine state the means are close. For example, the matched-power 4080 run had gaps of 1 to 3% within a stable block, and 10 to 25% for the light-rate cells known to have run at a lower power mode.
- **Where it shows:** `summary.json` holds `power_check`, with one row per cell, and `warnings`. The generated report prints every warning at the top, plus the per-cell table next to each run. `compare` lists the mean power of each entry and warns about each pair of entries whose means differ by more than the tolerance, so entries from different power states cannot be compared without a warning. A flagged cell is still scored; whether to repeat its block is decided and written down before the repeat, as in [Repeating blocks](#repeating-blocks).
- Fixed actions and policies that are meant to be compared run in the same randomised block: give `--actions` and `--policies` together.

`summary.json` holds per-cell counts and the mean GPU power of each cell, per-rate and per-action results with intervals, and all pairwise action differences per rate. `scored.jsonl` holds one record per target job.

## Commands

Run with a Python environment that has `transformers` (for the tokenizer) and, for scoring, `math_verify`.

```sh
python 15_matched_real_answers.py prepare \
  --prompts /absolute/path/prompts.json --labels tcr_results/main/rollouts_v2 \
  --out /absolute/path/new-plan-directory --questions 50

python 15_matched_real_answers.py run \
  --plan /absolute/path/plan-directory/plan.json \
  --calibration /absolute/path/calibration-directory/calibration.json \
  --lengths tcr_results/main/lengths_v2.json --prompts /absolute/path/prompts.json \
  --hardware-json /absolute/path/hardware.json --out /absolute/path/new-run-directory

python 15_matched_real_answers.py score \
  --out /absolute/path/run-directory --gold /absolute/path/plan-directory/gold.json
```

## Resuming an interrupted run

A cell takes about 22 minutes on the 4080, so a six-entry block takes over two hours. That is longer than a 2-hour cluster job, and a spot VM can be reclaimed at any time. `resume` continues a run at its next unfinished cell:

```sh
python 15_matched_real_answers.py resume --out /absolute/path/run-directory [--deadline-epoch EPOCH] [--url URL]
```

- **Same protocol only.** Resume rebuilds the run from its stored configuration and refuses to continue if the plan, calibration, lengths, rates, window or policies have changed. It also refuses code at a different commit unless `--allow-new-commit` is given; in that case the new commit is recorded for the segment. Traces and cell orders are read from disk, never regenerated.
- **Completed cells are never touched.** A cell counts as complete once it is listed in its block's `cells.json`. Every JSON file is written to a temporary file and then renamed, so a stop mid-write leaves the old file in place.
- **Partial cells are discarded, never scored.** The manifest names the cell in progress before it starts. On resume, that cell and any of its files that are not in `cells.json` are moved to `BLOCK/discarded/segment-K/` and listed under `discarded`. The cell then reruns from the start on the same trace.
- **Segments.** A segment is one harness process against one server process, and `segments` in the manifest records the start, commit, process id and server start time of each. When a block continues in a new segment after its control already ran, it first runs an extra control, `cell-sK-control-N0-B0`, so that every segment has its own machine-state check. The power-state check compares each cell with the control of its own segment. If the block's own control has not run yet, it simply runs in the new segment.
- **Server restarts.** The server start time comes from `process_start_time_seconds` in `/metrics`. If it changes during a cell, the cell is not recorded and the run stops with status `failed`, so it can be resumed in a new segment. A server that has stopped responding fails the run the same way.
- **Stops.** SIGTERM (a Slurm time limit, or a spot shutdown) and Ctrl-C mark the run `interrupted`. `--deadline-epoch` stops before a *cell* that could not finish in time and marks the run `partial_deadline`. In both cases the run is resumed later. Only blocks listed under `completed` are scored.

## Repeating blocks

A block that ran while the machine was in a different state (for example at reduced GPU power) is repeated with `run --seeds SEED --rates LABEL=RPS` under a new output name, never by overwriting. `assemble --blocks RUN_DIR/BLOCK ... --out NEW_DIR` then copies the kept blocks of the original run and the repeated blocks into one directory that `score` reads like a single run. Every source must share the plan, calibration, window and latency targets, and a repeated block must use the frozen value of its rate; the manifest lists the run, commit and start time of every block, and the interpretation must say which blocks were repeated and why.

## Limitations

- A cell that ran at lower GPU power than the others (laptop power state, thermal limits) is slower for reasons outside the experiment. The power-state check flags it, but the check only detects a power gap; it cannot correct for one.
- One machine. Intervals come from resampling questions; with three seeds they say little about run-to-run variation of the server itself.
- The background is synthetic, so the comparison says how an action behaves next to calibrated traffic, not next to other users' real answers.
- The GPU-second attribution is by generated tokens. Two actions with the same token count but different batch shapes are charged the same.
- Fixed actions and frozen per-job policies only; no learned router. A policy result is a gain over a fixed action only where the paired interval against that action excludes zero.
- Target jobs are spaced evenly, not Poisson, so target-on-target bursts are not exercised.

## Tests

`tests/test_matched_real_answers.py` covers cohort selection, the matched target schedule and the bootstrap with fixed inputs, and runs `run` and `score` against `test_fake_vllm_server.py`, which answers every real request with a fixed boxed answer.
